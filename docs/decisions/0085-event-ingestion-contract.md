# Event ingestion contract

## Context and Problem Statement

The events that **0083** models and the aggregation-strategy record reduces have to enter the
system somehow. CAPCOM is a **seeded** demo — the bulk of its data is generated by a seed script
— but a portfolio piece about a product-analytics platform that shows *no* intake path is
unconvincing. This record decides the **single demonstration ingest path**: how an external
product sends a batch of events into a project, how that call is authenticated and validated,
and what it returns on success and failure. It also records, as a first-class decision, the
**seeded-data posture** — that this is one demonstration route and explicitly *not* a
high-volume pipeline or client SDK — so the absence of that machinery reads as a conscious scope
boundary rather than an omission.

The decision sits on settled conventions: route handlers for webhook-style endpoints (**0002**),
Node-first route runtime (**0004**), Zod as the single validation authority at every boundary
(**0017**), structured-error semantics with generic client-facing messages (**0019**), and the
**0013** rule that trusted server-only credentials never reach a user context. The open
questions are the *transport* (route handler vs Server Action vs SDK vs direct client insert)
and the *credential* (who is allowed to write events, and how that is proven).

## Decision Drivers

* **Ingestion is server-to-server, not a member action.** The caller is *a product emitting
  events*, not a logged-in member — so session auth (**0016**) is the wrong credential; a
  per-project key is the right one.
* **The write must stay inside one tenant.** Whatever authenticates the call must resolve to
  exactly one `project`, and the events must be written with that `project_id` and no other —
  honoring the **0083** isolation model even though the actor is not a member.
* **Validate at the boundary (0017).** An untrusted external payload must be parsed by a Zod
  schema before anything touches the database; types are inferred from it.
* **Structured, generic errors (0019).** Validation and auth failures return a structured error
  contract; client-facing messages stay generic.
* **Demonstrate, don't build a pipeline.** The goal is to show the *contract* (auth + validation
  + structured response), not throughput — the seeded posture is deliberate.
* **Webhook-style ⇒ route handler, Node runtime (0002/0004).** A machine-to-machine POST is the
  textbook route-handler case, not a Server Action (which targets member-driven mutations).

## Considered Options

* **A — A single Route Handler `POST /api/ingest`**, Node runtime, Zod-validated event batch,
  authenticated by a per-project ingest key.
* **B — A Server Action** for ingestion.
* **C — A full client SDK + high-volume pipeline** (queue/stream, batching, retries).
* **D — Direct client → Supabase insert**, authorized by member RLS.

## Decision Outcome

Chosen option: **A — a single `POST /api/ingest` Route Handler**, because it matches the
webhook-style/server-to-server shape exactly (**0002**), runs on the Node runtime (**0004**),
validates the untrusted batch with a Zod boundary schema (**0017**), and authenticates with a
**per-project ingest key** that resolves to one tenant — the only credential model that fits a
non-member actor while honoring the **0083** boundary. B mis-models a machine call as a member
mutation; C builds infrastructure the seeded demo consciously excludes; D would require the
emitting product to hold a member session and would route writes through member-RLS, which is
not who is calling.

The contract this record fixes:

* **Endpoint & runtime.** `POST /api/ingest`, Node runtime (**0004**), webhook-style route
  handler (**0002**) — not a Server Action.
* **Authentication — per-project ingest key.** The request carries
  `Authorization: Bearer <ingest_key>`. The key is **per project**, stored **hashed at rest**,
  and resolved server-side to exactly one `project_id`. It is a secret: provisioning, rotation,
  and revelation are human-governed (the secrets policy), never an agent action. No member
  session is involved.
* **Payload — Zod boundary schema `[ingest]`.** A bounded **batch** of events, each
  `{ event_name, distinct_id, properties, ts? }`, parsed and type-inferred per **0017** before
  any database write; an absent `ts` defaults server-side. Batch size is capped.
* **Write path — confined server-side insert.** Validated events are inserted into `events`
  stamped with the **resolved** `project_id`. Because the actor is not a member, this write runs
  in a **trusted server-only context** (the **0013** boundary) rather than under `auth.uid()`
  RLS — the ingest key *is* the authorization, and the handler is the only place that mints the
  `project_id`, so a payload cannot target another tenant. This trusted path is confined to the
  route, server-only, and never reaches the client (**0013**).
* **Response — structured contract (0019).** Success returns an accepted-count; failures return
  a structured error with a stable code — `401/403` for a missing/invalid key, `422` for a
  schema violation — with generic client-facing messages and structured server logs.
* **Scope boundary (recorded).** This is the *single* demonstration route. No SDK, no batching
  queue, no streaming, no backpressure, no at-scale idempotency. Data volume comes from the seed
  generator; this route proves the contract.

### Consequences

* Good, because it demonstrates a production-shaped intake contract — per-tenant auth, boundary
  validation, structured errors — at minimal cost.
* Good, because the per-project ingest key is honest server-to-server authentication, decoupled
  from member identity.
* Good, because the Zod boundary keeps payload types inferred and re-validated at the trust
  edge (**0017**).
* Good, because it stays within settled conventions (**0002/0004/0019**) and the **0012**
  baseline.
* Bad, because it introduces a **non-member write path** (the ingest key) that bypasses
  member-RLS — contained by resolving the `project_id` server-side, keeping the trusted path
  server-only (**0013**), and treating the key as a secret rotated under human governance;
  audited by the `security-reviewer`.
* Bad, because there is no rate-limiting, deduplication, or queue — a real concern at volume,
  consciously out of scope and recorded as such.
* Bad, because the ingest key is long-lived shared state per project; rotation is a manual,
  human-only operation (acceptable for a demo, named explicitly).

### Confirmation

* A route test exercises the contract: a **valid batch** is accepted and the rows land scoped to
  the resolved project; an **invalid payload** returns `422` with the structured error shape; a
  **missing/invalid key** returns `401/403`.
* The Zod `[ingest]` schema is the sole parser at the boundary; types are inferred from it
  (**0017**) — no hand-written request type.
* The route declares the **Node runtime** (**0004**) and is a route handler, not a Server Action.
* The `security-reviewer` confirms the ingest-key path is **server-only**, the write is confined
  to the **resolved** `project_id`, the key is compared against a hash (never logged), and no
  service-role/trusted credential reaches client code (**0013**).

## Pros and Cons of the Options

### A — Route Handler `POST /api/ingest` with a per-project ingest key

Webhook-style Node route; Zod-validated batch; key resolves to one tenant; confined server write.

* Good, because it fits the server-to-server shape and the **0002/0004** conventions exactly.
* Good, because the per-project key models a non-member actor honestly and bounds the write to
  one tenant.
* Good, because Zod validates the untrusted payload at the boundary (**0017**).
* Neutral, because it adds one secret per project to manage (hashed, human-rotated).
* Bad, because it is a non-member write path that must be carefully confined server-side.

### B — Server Action for ingestion

* Good, because it reuses the Server Action mutation path.
* Bad, because Server Actions model **member-driven** mutations bound to a session, not
  machine-to-machine intake — the wrong abstraction for an external emitter.
* Bad, because it would entangle ingestion with member auth/CSRF semantics that do not apply.

### C — Full client SDK + high-volume pipeline

* Good, because it is what a real analytics product ships.
* Bad, because it builds queues, batching, retries, and backpressure the seeded demo explicitly
  excludes — large scope for no demo value.
* Bad, because it would need its own ADRs and likely Supabase capabilities outside the **0012**
  baseline.

### D — Direct client → Supabase insert under member RLS

* Good, because it needs no new endpoint.
* Bad, because the emitting product is **not a member** — it has no `auth.uid()` and should not
  hold a member session.
* Bad, because routing intake through member-RLS conflates the tracked end-user with the
  authenticated member — the precise collapse **0083** forbids.

## More Information

This record completes the intake side of the **0083** event model: the per-project key writes
events that the aggregation-strategy record reduces and the charting record renders. It rests on
**0002** (route handlers for webhook-style endpoints), **0004** (Node runtime), **0017** (Zod
boundary validation), **0019** (structured errors), and the **0013** trusted-server-only
credential boundary, inside the **0012** baseline. It is realized by the PR-3 ingest route and
the `events` write path, alongside the seed generator that supplies the demo's data volume. The
seeded-data posture is the recorded scope boundary; revisiting it (a real SDK or pipeline) is a
new decision, not an edit to this one.
